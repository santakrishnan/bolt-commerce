3. Landing Page Variations & Personalization Logic

Overview of Variations

• Three main landing page variations tailored to different user contexts:

• First time user experience:

• Identified using fingerprint.com for device fingerprinting; along with session ID, creates a unique user profile.

• Client-side and server-side calls coordinate to gather fingerprint, IP, geolocation, and session info.

• Info is stored in cookies with a 24-hour lifetime.

• Returning user (unauthenticated or not logged in):

• Determines time since last activity using cookie-stored info.

• 

3 hours inactivity triggers a different landing page experience.

• Dynamic ID information; actual data retrieved from backend APIs using IDs.

• Returning user (authenticated):

• Personalized landing page, e.g., “Welcome back James”, shows recent activity, CTA to complete unfinished steps (e.g. prequalification, test drive booking not completed).

• If authentication remains after 3+ hours, user still gets personalized landing.

Feature Flags & API Integration

• Demo version uses a feature flag to swap between landing page variations, but in production, personalized landing will be decided by API responses.

• The plan is for backend APIs to return contextual user info (e.g., new/returning/authenticated).

Questions & Clarifications

• Clarification on when client vs. server uses Fingerprint API.

• Data in cookies is primarily IDs; actual info is retrieved on demand via backend calls.

• Location and best-match vehicle calls: Discussion on optimal server/client handling.

4. State Management & Data Fetching

• Use of Tanstack Query for persistent state on the client.

• On saving/favoriting vehicles:

• State is updated via Tanstack, which manages API sync.

• Removal/fallback behavior if API calls fail is in place.

• Recommendation was given to pre-fetch server state (e.g., saved vehicles) and pass as initial state to Tanstack on first render, with normal client management thereafter.

5. Dynamic vs. Static Rendering & Caching Patterns

• Use of Next.js 16 (Turbopack, App Router, Cache Components) is confirmed.

• Landing page includes dynamic components (e.g., “HERO banner” block with live ratings, vehicle stats) and discussion centers on optimizing server vs. client data delivery, suspense boundaries, and revalidation/caching.

• Some blocks can be statically rendered and revalidated (&quot;revalidate it&quot;), others are dynamic.

• Guidance around cache strategy: Centralizing cache configuration in next.config, establishing “cache profiles” for reuse (e.g., for images, vehicles).

• Noted that with cache components, not all dynamic child components force the parent to be non-static.

6. Stack & Tooling Overview

• Stack highlights:

• Next.js 16, cache components, Turbopack monorepo

• Tailwind, PNPM, Biome, Ultrasight (linter), Tanstack Query, Framer Motion, JOS (encryption), Zod (schema validation), Vitest

• Encrypted event tracking (using JOS) for client events

• Localized font loading with next/font from the public directory

• All code is in TypeScript

• Mock APIs currently in use; plan is to proxy all backend API calls through app-level API wrappers for modularity, logging, encryption, future-proofing.

7. Monorepo & Folder Structure

• Current structure:

• Reusable primitives/components in a UI package (meant to be “very thin” for now, makes white-labeling/theming easy in future)

• Application-specific components kept separate but may be migrated to UI/UI-theme if generalized/reusable.

• Use of theming (Figma-driven), with the ability to override base tokens for rapid white labeling.

• Request for feedback and recommendations, especially around centralized caching and extensibility.

8. SEO Routing & Catch-All Segments

• Current page routing uses a &quot;used-car&quot; catch-all segment for vehicle listing/detail pages.

• Partial page reactivity (only user-context specifics, e.g., the right-side summary block, are dynamic).

• Open for SEO recommendations; aim to cache most content server-side and only personalize or vary required blocks.

9. Provider Structure & Application Context

• List of application-level providers was reviewed (e.g., PaperProvider, CardProvider, SearchProvider).

• Recommendation: Only wrap what is needed with each provider; overuse could cause unnecessary re-renders.

• Action: Review and modularize providers to reduce unnecessary state passing.

• Discussion about centralizing providers vs. colocating only where required.

10. Component/Feature Organization: Screaming Architecture

• Concerns raised about scalability of the current “giant components folder” as features grow.

• Suggestion (screaming architecture pattern):

• Organize by feature/module (“feature folders”) each with its own components, hooks, data, etc.

• Benefits: Easier navigation, modularity, portability (move a feature, not just a component), better encapsulation.

• Andrew and Gonzi to review sample reference repo implementing this pattern, access given post-meeting.

• Debate on how/when to migrate generic UI logic to the UI package if cross-app reuse is required.
